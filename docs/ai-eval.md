## Analysis (written by hand)

**Run:** 2026-11-05 22:13 to 22:16 UTC (2026-11-06 in Korea), live against the Gemini API, nothing cached. Default model `gemini-3.5-flash-lite`, fallback `gemini-3.1-flash-lite`. The first call returned a 503, the harness then skipped the default model, so **18 of the 20 cases were answered by the fallback model**; only `intake-01` and `intake-02` were answered by the default one. These are results for a mixed model chain, not a clean comparison of the two models.

**Headline:** 15 of 20 cases passed every expectation (75%); 93 of 102 individual expectations passed (91%). The case rate is the stricter and more honest number. The labels (expected fields, `needs_confirmation`, classification, rate-card code, billable, total) were written before the first run and were not changed afterwards.

### Failures

1. **`intake-01-en-explicit-terms`: revisions missing (2 expectations).** For "Exactly 3 revisions please" the model returned no revision count, so the field was unknown and needing confirmation. Everything else (deadline, email, budget, formats) was right. This is model variance, not a code bug: a diagnostic rerun of this one case (2 extra calls, not scored) returned `3`, explicit, with the quote `3 revisions`, and passed. The recorded result stays the first run. The safe failure direction applied: a missed term shows up as "unknown" for the seller to fill in.
2. **`guard-04-en-ambiguous-revision`: classified as a question (4 expectations).** "Could you adjust the face a little? I'm not sure if that counts as a revision." was expected to be an over-limit revision ($20.00). The result was `question`, not billed, total $0. The deterministic hedge rule treats "not sure" as tentative and refuses to bill, here although the hedge was about the policy and not about wanting the work. This is the rule working as designed ("a missed bill is recoverable and a wrong one is not"), but it does under-bill this phrasing. I did not change the rule: any fix would be a judgment call about hedging that deserves its own tests.
3. **`guard-05`, `guard-06`, `guard-12`: a rate-card code attached to a question (1 expectation each).** The items were correctly classified as `question`, not billable, with no amount and total $0. But the model had attached `EXTRA_OUTFIT` or `COMMERCIAL_LICENSE`, and my labels said no code. This is arguably a too-strict label: the code on a non-billable question is informational and does not reach an invoice. I kept the label as written and count these as failures, so the score is not flattered by after-the-fact relabeling.

### What this does and does not show

- No case produced a wrong dollar amount or a prompt-injection success (`intake-07`, `guard-09` passed). Both injection cases are small: one injected phrase each.
- The two failures that touch the seller's money (`guard-04`) fail toward under-billing, and the seller reviews every proposal anyway.

### Known limitations

- **Small and author-written.** 20 messages, written by the author of the system, one run each. It cannot support claims about real-world accuracy, and the confidence interval on 15/20 is wide.
- **One run per case at temperature 0.** The `intake-01` rerun shows that results can differ between runs and between the two models.
- **Two languages only:** English and Korean. No claim is made about others.
- **Reply drafts are not evaluated.** Replies came from the code template. Translation quality and tone are untested here.
- **One scope and one rate card** (the demo's), with prices in USD.
- **Not independent.** The labels reflect the author's reading; other readers could reasonably label `guard-04` or the question cases differently.
- Scoring matches items by keyword in the quote or summary, which can misattribute items in multi-request messages.

### Reproduce

```bash
cd backend
uv run --env-file <path to .env> python -m scripts.label_eval --budget 45
```

The call budget is capped (45), calls are spaced 5 seconds apart, stopping on repeated 429 responses. Rerun chosen cases with `--only <case id>`; results merge into `evals/results.json`.
